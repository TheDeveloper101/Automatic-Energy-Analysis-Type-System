Our type system Heliod has two primary goals: keeping track of peripheral state as accurately as possible, and using this information to obtain symbolic cost bounds on programs. To achieve these goals, we use a combination of typestate and cost analysis in order to provide robust and precise bounds. We aim to provide symbolic bounds to allow programmers to reason about the cost of their programs at a high level without needing to worry about particular hardware details. 

\subsection{Heliod Basics}
Heliod has to consider three main categories of costs when performing it's cost analysis: we have cost from executing statements of code on the main processor, cost from actively using a peripheral, and cost from peripherals that are active in the background. Typestate in particular helps us to reason about the latter two categories of cost due to the fact that a peripheral's program cost will vary based on it's internal state. While we can naively overapproximate the cost of using a peripheral by taking it's most expensive state and using it throughout, such an approach will result in bounds that are sound but far too overapproximate to be useful. 
\paragraph{Simple Example}
To explain how our type system works, we will first start with a simple example found in ~\autoref{fig:cost_analysis_example}, and then progressively introduce additional features and complexities that are needed for our system to be applicable to real embedded system programs.

The example program models a simple task using a temperature sensor. The function \texttt{log\_data()} takes a temperature sensor as input, and immediately transitions it to the \texttt{Measure} state. This allows for the sensor to perform a measurement. Once doing so, it will conditionally write to a variable based on the result of this measurement, before turning the sensor off and then returning the written value. Peripherals are modeled as a lattice with downgrading policies. This is essentially like a state machine, but the lattice structure allows for ease of modeling. The explicit 
\texttt{transition} and \texttt{downgrade} statements are used specify that a peripheral's state is changing from it's current state to the new state specified by the statement. A \texttt{transition} moves a peripheral's state up the lattice, and a \texttt{downgrade} moves it down. In order to report costs accurately, we need to determine which portion of the total overall cost can be charged to each of the three categories mentioned before: peripheral operations, background peripherals, or general code statements. We do this by broadly having three different types of cost expressions. The expression $C(p : st)$ refers to the cost of a peripheral $p$ being in a concrete state $st$. $C(p : (st, st'))$ refers to the cost of peripheral $p$ transitioning from $st$ to $st'$, and a plain $C$ refers to cost from main board execution with a possible subscript to identify it. For branches, we use a \texttt{max} operation to account for cost in places where the branch taken isn't statically known. In \autoref{fig:cost_analysis_example},  $C_v$ refers to the cost from writing to a variable. To provide the total cost bound, we analyze each statement individually, along with adding any possible background peripheral costs. Then we combine all of the cost statements to derive the total function cost. The main resources that we are interested in bounding are execution time and energy consumed. Both of these resources rely on the passage of time. To support our goal of providing a high-level symbolic bound for reasoning about programs, we reason about such resoruces in terms of logical timesteps, where one logical timestep corresponds to one command. 

\paragraph{State Inference}
In the example, the first cost expression is $C(\text{temp}:(\alpha_0,\text{Measure}))$ which was not covered before. This is due to the fact that the state of the temperature sensor at the beginning of \texttt{log\_data()} is not known. In fact, the initial state depends entirely on how the temperature sensor is used prior to \texttt{log\_data()} being called. To provide this insight, there are a number of alternatives. The first option is that we require programmers to annotate the intial state of each passed in peripheral. This is conceptually the easiest option, however it presents many complications. First, it requires programmers to know the exact state of the peripheral for every place the function can be called. For simple peripherals such as a temperature sensor, this can be possible. However for more complicated peripherals such as a UART driver or a radio, attempting to determine the exact state can be very difficult, and result in unnecessary annotation burdens, as well as increasing the potential for errors. 

In contrast, our approach is to utilize a variant of type inference that we call \textit{state inference}. To make this concrete, we will consider the examples in \autoref{fig:usage_example}

Here we have two different ways of using \texttt{log\_data()}. In the program on the left, the temperature sensor is  transitioned to the \texttt{Idle} state, and then immediately passed into \texttt{log\_data()}. In the program on the right, it transitions the temperature sensor all the way to the \texttt{Measure} state and performs a measurement prior to calling \texttt{log\_data()}. Importantly we want to support both possible uses of \texttt{log\_data} because a programmer may choose to perform additional measurements prior to calling the function. Requiring peripheral state annotations means that a programmer is forced to choose between one of the two use cases. One potential solution to this is to support "state polymorphism" where the function can accept either state. However the issue is that this can result in bounds being unnecessarily conservative as the analysis will not know the exact state passed in leading to overapproximation, and we need the cost bound to be sound regardless of what state is passed in. With state inference, we are able to determine the exact state a peripheral will be in at the call site, therefore allowing for tighter bounds. To show how it works, we use \autoref{fig:concretization-and-inference} as an example.

\begin{figure}[h]
  \centering
  \small

    \texttt{\quad transition(temp, Idle);} & temp = $[\alpha'_1 :: \alpha'_0],$ \\ \text{} & $\Phi = \alpha'_1 = \texttt{Idle} \land \alpha'_0 \leq \alpha'_1$ \\
    \texttt{\quad let t = log\_data(temp);} & $\m{solve}(\alpha'_1, \Phi \land \alpha'_1 \leq \texttt{Measure}) = \texttt{Idle}$ \\
    \texttt{\}} & temp = $[\texttt{Off} :: \texttt{Measure}  :: \texttt{Idle}:: \texttt{Off}]$\\
  \end{tabular}
  \vspace{-6pt}
  \caption{Concretization and Inference Example.}
  \label{fig:concretization-and-inference}
\end{figure}

At the start of \texttt{main()}, we have no knowledge of the state of the temperature sensor. As a result, the algorithm starts by assigning it a state variable $\alpha$---analogous to a type variable---and storing it in a \textit{stack}. This is because every time it encounters a \texttt{transition} or \texttt{downgrade} statement, it will create a new state variable and push it onto the stack associated with the peripheral. This stack is represented by $[\alpha]$, and allows the algorithm to maintain an SSA-like property. This is useful for understanding how peripheral state evolves over time, as well as keeping track of what state is the most current. 

Because the program transitions to the \texttt{Idle} state, the inference algorithm adds the constraint that $\alpha'_0 \leq \alpha'_1$ since that is required for the transition to be valid. When the algorithm reaches \texttt{log\_data()} function call, it combines the constraints it has collected thus far with any constraints known within \texttt{log\_data()}. In this case, it know that \texttt{temp} will transition into the \texttt{Measure} state, so it has the constraint that $\alpha_0 \leq \texttt{Measure}$, where $\alpha_0$ is the state of $\texttt{temp}$ on entry to \texttt{log\_data()}.To solve for the initial state, the algorithm renames $\alpha_0$ to be $\alpha'_1$ since $\alpha'_1$ refers to the current state of the temperature sensor. Then, it takes all of those constraints and solve for them giving the solution $\alpha'_1 = \texttt{Idle}$. We refer to this process as \textit{lazy} concretization of $\alpha_0$ since we chose not to solve for it until \texttt{log\_data} was called and we had additional information about the temperature sensor's state. On the flip side, we were immediately able to solve for the state of the peripheral after line 8 in \texttt{log\_data} since the peripheral's state only depends on the state of the peripheral after line 2 which is fully known. This is what we refer to as \textit{eager} concretization.

To represent the cost of peripherals in an unknown state prior to concretization, we introduce two additional cost expressions. We use $C(p : \alpha)$ represents the cost of a peripheral being in an unknown state $\alpha$ and $C(p : (\alpha, st))$ to represent the cost of transitioning from an unknown state to a concrete one. Using this information, it allows us to derive the following cost bound for \texttt{main}: $C(\text{temp}: (\texttt{Off}, \texttt{Idle})) + C_l[\alpha_0 \mapsto \texttt{Idle}]$ where $C_l$ refers to the cost bound for \texttt{log\_data} derived earlier. At the very end of \texttt{main}, the temperature sensor stack is given by $[\texttt{Off} :: \texttt{Measure} :: \texttt{Idle} :: \texttt{Off}]$, where the latter two states come from analyzing \texttt{log\_data()}.

\subsection{Asynchronous Operations}
As mentioned in Section 2, embedded systems commonly exhibit hardware-software concurrency. The primary difficulty with this is that the state of peripherals can be changed by hardware \textit{automatically} and in a manner that is invisible to software. This provides an immediate challenge as such a change can potentially violate invariants that Heliod depends on to ensure peripheral's are used correctly and the cost analysis is accurate. In order to deal with this, we follow Abacus \cite{abacus} and define a separation between peripheral states. We have \textit{stable} states which are states where all of the incoming and outgoing transitions are governed by software. Any state that has \textit{at least} one transition governed by hardware is marked as \textit{unstable}. This means that if a peripheral is in an unstable state, it can transition from it at any time, even without needing to notify software. 

We use \texttt{async/await} syntax to represent the hardware-software concurrency exhibited by unstable states. Furthermore, we require that such operations are \textit{peripheral capturing}, meaning the peripheral is no longer available to the main program until the operation completes. This allows us to model the concurrency exhibited by peripherals as they will be able to perform their own operations while the main program executes.

In this example, we update the temperature sensor lattice to be the following states: [\texttt{Off}, \texttt{Idle}, \texttt{Warmup}, \texttt{Conv}, \texttt{Ready}] where \texttt{Off} < \texttt{Idle} < \texttt{Warmup} < \texttt{Conv} < \texttt{Ready}, and there are downgrade policies from \texttt{Warmup}, \texttt{Conv}, and \texttt{Ready} to \texttt{Idle} and from \texttt{Idle} to \texttt{Off}. The \texttt{sample()} function takes in a temperature sensor and a buffer passed in called \texttt{buf}. It then transitions the temperature sensor to the \texttt{Warmup} state and then asynchronously moves to the \texttt{Ready} state. While this asynchronous operation is occurring, the function calls \texttt{checksum()} on the buffer passed in, which already has a derived bound of $C_k$. Then once the \texttt{checksum()} function completes, the temperature sensor is awaited, and if timed out gets downgraded to idle. Finally, depending on the result of the asynchronous operation, we write either 1 or 0 to a variable. For simplicity's sake, we elide the state inference that is occurring in this example. 

The interesting parts of the cost analysis have to do with the asynchronous call and await. When a peripheral is used asynchronously, we calculate it's cost separately. Then, since we require all asynchronous operations to be awaited, we perform the actual calculation for the cost there. At an await command, Heliod will take the maximum of performing the asynchronous commands and waiting for the timeout to trigger followed by code that runs if the timeout is triggered. For any commands in between the asynchronous call and the await, the captured peripheral is charged by taking the maximum possible cost across all of it's hardware reachable states. This is because we cannot guarantee the peripheral actually completes execution until the await. Finally, we require that at the end of the asynchronous operation that the peripheral returns to a stable state. This ensures that subsequent peripheral charges are charged accurately, and prevents the peripheral from potentially changing underneath of software.
